Recorded: 2026-11-14. Branch: `workstream-c/recipe-option-sets`, based on `main` at `753dc1e`
(after [recipe option limits](RECIPE_OPTION_LIMITS_LOCAL_EVIDENCE_20261114.md) merged). Step 2a
of [decision 0009](decisions/0009-recipe-option-sets.md): storage, server logic,
API and tests. The option-set screens (step 2b) follow once the pending UI
changes merge. **Local evidence only.** This change adds a migration; no other
schema-bearing change is pending.

## Changed behavior

- **Migration `0046_recipe_option_sets`** (additive) creates:
  - `recipe_option_sets`: the current revision of each company's set (name,
    kind `one`/`addons`, choices as JSON);
  - `recipe_option_set_revisions`: every saved revision, unique per operation;
  - `recipe_option_links`: which sets are attached to which recipe, with
    per-item overrides and the last applied revision.

  Sales and consumption never read these tables.
- **Service** ([`d1-recipe-option-sets.ts`](../src/lib/d1-recipe-option-sets.ts)):
  - **Saving a set** validates it: up to 40 uniquely named choices; a "pick one"
    set needs at least two choices, each adding an ingredient; products must
    exist in the company; choice names are fixed once saved. It writes a new
    revision only if the expected revision is still current, replays an
    identical operation, and rejects a reused operation with other details. It
    then republishes every attached recipe.
  - **Attaching sets** to a published recipe (up to 10) replaces that item's
    attachments and overrides. An override is allowed only for a choice with one
    ingredient and must be positive. The item is then republished.
  - **Applying** rebuilds the full recipe through the existing atomic
    `publishRecipe`: the active base ingredients, the item's own modifiers and
    choice groups, plus one generated modifier per set choice
    (`opt-<set>-<choice>`), with item overrides, and a choice group
    (`opt-<set>`) for "pick one" sets. Applying an unchanged item is a no-op.
    A failure is reported per item and leaves the attachment marked as not
    applied, so it can be retried.
- **API** (`/api/inventory`, exact inventory preview only):
  `saveOptionSetExact`, `attachOptionSetsExact` and `applyOptionSetsExact`
  require an owner or manager of the company and use the existing sign-in,
  cross-site and audit handling. Set and choice IDs are limited to 60 letters,
  digits or hyphens. The inventory read now includes `optionSets` for any
  company member.
- **Recipe builder:** editing an item keeps its option-set choices and groups
  unchanged (they are republished with the edit and count toward the 64-option
  limit) and says so; only the item's own choices and extras are editable.

## Schema review

- **SQL, snapshot and journal:** generated by `pnpm db:generate` from
  [`schema.ts`](../src/db/schema.ts) as `drizzle/0046_recipe_option_sets.sql`,
  `drizzle/meta/0046_snapshot.json` and one journal entry. Three new tables,
  one new index and one unique index; no change to existing tables, no
  triggers.
- **Fresh and populated databases:** `pnpm db:check` applied every migration
  to fresh SQLite; the migration also applied to a copy of the existing local
  development database (with prior recipes and sales).
- **Compatibility:** existing code ignores the new tables. Recipes without
  attached sets behave exactly as before.
- **Rollback / forward repair:** revert the code; the tables can stay unused.
  Never edit this migration once applied; a later additive migration can drop
  or reshape the tables. Recipes already republished from sets remain valid
  ordinary recipe versions.

## Verification

The complete local pipeline passed in this worktree on 2026-11-15 with the
changes staged on base `753dc1e`: `pnpm typecheck`, `pnpm test` (177 suites,
including the new and extended ones), `pnpm db:check` (47 ordered migrations
match the schema and apply to fresh SQLite), `pnpm build`,
`pnpm db:migrate:local` and `pnpm test:local`. The first full run found that
`tests/prepared-file-check-migration.mjs` assumed `0045` is the newest
migration; it now finds its migration by tag, like the other migration tests.
ESLint and Prettier are clean for the new files; the changed route and builder
stay Prettier-clean with no new ESLint findings.

- [`tests/recipe-option-sets.mjs`](../tests/recipe-option-sets.mjs), with a
  local D1 stand-in that rejects more than 100 bound values per statement:
  create, replay and reused-operation conflict; four invalid sets refused;
  attachment with an item override producing the expected generated modifiers
  and "pick one" group while keeping the item's own "Extra shot"; refused
  overrides (unknown choice, zero, negative, a two-ingredient choice) and
  unknown recipe; a sale applying base, oat milk at the override, two syrups, a
  no-change ice option and an extra shot; a sale without milk held; a set edit
  republishing only the attached item, keeping the override, refusing stale and
  renaming saves, while an earlier sale keeps the earlier amount; an unchanged
  re-apply as a no-op; detaching every set; and company isolation. Eleven
  deliberate code mutations: ten made the test fail; the eleventh removed the
  early revision check, which the database-level revision guard still enforces
  (covered by a stale-update case).
- [`tests/m2-security.mjs`](../tests/m2-security.mjs): the three new actions
  join the per-action cross-company and cross-site checks; anonymous (401),
  other-company, employee and wrong-company manager requests (403) are refused;
  invalid set IDs return 400; a manager save and attach succeed; employees can
  read option sets; a stale save returns 409.
- **Local browser check** with the exact preview enabled: a set saved and
  attached through the API produced the two generated modifiers; opening that
  recipe in the builder showed "2 option-set choices … will be kept", and
  saving it published version 3 with both option-set modifiers still active. No
  page errors.
