# W4b photo waste suggestions (server, fake reader) — local evidence

Recorded: 2026-11-16. Branch: `workstream-c/photo-waste-w4b`, based on `main`
at `8d5d9dc`. Step W4b of the
[photo waste plan](WASTE_AND_MARGIN_ROADMAP.md#w4--photo-waste-suggestions),
following [decision 0010](decisions/0010-photo-waste-suggestions.md). **Local
evidence only, with the offline fake reader.** No paid or external service was
called. Adds migration `0051`; no other schema-bearing change is pending.

## Changed behavior

- **New endpoint `POST /api/waste/suggestions`**
  ([route](../src/app/api/waste/suggestions/route.ts),
  [handler](../src/lib/waste-suggestion-route.ts)):
  - It sits behind the existing waste route wrapper, so the same rules apply as
    for recording waste: owners, managers and employees of the company, a
    signed-in person, same-site requests, and audit entries. It also requires
    the exact inventory preview.
  - The body is `{companyId, operationId, note (≤300), photo: {mediaType,
    data}}`. Any other field, including a client-supplied actor, is refused.
  - It returns suggestions only; **nothing is recorded as waste.**
  - Without an explicit server setting it answers "Photo suggestions are not
    available yet". In this step the only reader is the offline fake
    (`PANTRACK_WASTE_READER=fake`), which is never set in the checked-in
    configuration.
- **Photo checks**
  ([contract](../src/lib/waste-suggestion-contract.ts)): only JPEG, PNG or
  WebP. The decoded bytes must start with the matching file signature and be at
  most 1.5 MB, the browser's resize target in W4c.
- **What the reader may suggest** (`D1WasteSuggestions.catalog`):
  - menu items that are ready and offered (ready-made products and recipes);
  - stocked ingredients, with a ready-made product listed only once, as its
    menu item;
  - each under an opaque reference (`m1`, `i2`), so internal IDs never reach
    the reader;
  - only the company's own items.
- **Untrusted output is checked** (`checkedEntries`):
  - only listed references, each once, up to 5 entries;
  - menu items need a whole quantity from 1 to 999;
  - ingredients need a positive decimal, or no amount when the photo cannot
    show one ("spilled oat milk"), which the person then fills in;
  - unknown reasons become "other", and explanations are cut to 200
    characters.
- **Requests** ([service](../src/lib/d1-waste-suggestions.ts),
  [migration 0051](../drizzle/0051_waste_suggestions.sql)):
  - Each request is claimed by its operation ID before reading. A repeat
    returns the saved answer without reading or billing again. A reused ID
    with another photo or note is refused.
  - A read left unfinished for over two minutes is reported as failed, never
    read again.
  - Recorded: the signed-in person, note, status, entries, provider, model,
    tokens and estimated cost (for the W4d cap). The photo is never stored,
    only its SHA-256 fingerprint inside the request fingerprint. Columns for
    the person's outcome (confirmed, edited, discarded) wait for W4c.
- **The fake reader** reads "5 croissants", "spilled an oat latte" or "spilled
  oat milk" from the note, ignores the photo, and costs nothing.

## Schema review

- **SQL, snapshot and journal:** the table, two check constraints (status and
  outcome) and the company/time index were generated by `pnpm db:generate`
  from [`schema.ts`](../src/db/schema.ts).
- **Fresh database:** `pnpm db:check` applied all 52 migrations to fresh
  SQLite. `pnpm db:migrate:local` applied `0051` locally.
- **Compatibility:** the change is additive and nothing reads the table yet
  outside this endpoint.
- **Rollback / forward repair:** revert the code; the table can stay. Never
  edit this migration once applied.

## Verification

The complete local pipeline passed in this worktree on 2026-11-16 with the
changes staged: `pnpm typecheck`, `pnpm test` (181 suites), `pnpm db:check`
(52 migrations), `pnpm build`, `pnpm db:migrate:local` and `pnpm test:local`.

- [`tests/waste-suggestions.mjs`](../tests/waste-suggestions.mjs) covers:
  - **photos:** valid JPEG, PNG and WebP; refused for a mismatched type, a PDF,
    an oversized file, bad base64 or a note over 300 characters;
  - **checking:** unknown references, duplicates, bad quantities, unknown
    reasons, long explanations and more than five entries;
  - **the catalog:** refs instead of IDs, ready-made items once, unready items
    excluded, company isolation;
  - **fake reader results:** 5 croissants (end of day), a spilled oat latte,
    spilled oat milk with the amount left to the person, and nothing guessed
    for an unrecognisable note;
  - **another company:** a reader naming `m1` for company B only reaches B's
    own item;
  - **no effect on stock:** no inventory event or balance changes;
  - **replays and races:** replays without reading, conflicts on a changed
    photo or note, concurrent repeats read once, and a forced race where
    another attempt claims between check and claim does not read;
  - **failures and usage:** a reader failure is recorded and not retried, a
    stale pending read is reported as failed without reading, usage and cost
    are recorded, the photo is never stored, and the database checks refuse
    unknown statuses and outcomes.
- [`tests/m2-security.mjs`](../tests/m2-security.mjs) covers:
  - unavailable without a reader (503), anonymous (401), other-company member,
    wrong-company manager and cross-site requests (403);
  - a client-supplied actor and a mismatched photo type (400);
  - an employee's request suggests the company's milk with no amount and
    records no waste;
  - the stored actor is the signed-in person, the photo is not stored, and the
    request is audited like waste.
- **Mutations:** nine deliberate code mutations were tried, and eight made a
  test fail:
  - duplicates kept;
  - bad menu quantities kept;
  - photo signature unchecked;
  - conflicts ignored;
  - ready-made items listed twice;
  - the reader always on (security test);
  - no claim before reading, and unready menu items offered. These two were
    first missed; the forced-race test and an unready item were added, and
    both then failed.

  Removing the replay check alone did not cause a second read, because the
  claim still stopped it (defense in depth).
